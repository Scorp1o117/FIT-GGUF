# FIT-GGUF v0.2 Proposal: Quality-Aware Span Selection

Recorded 2026-08-30 per owner direction ("先记录在项目里，之后再说").
Status: PROPOSAL ONLY - not preregistered, not scheduled. Execution
requires a new preregistration and third-model validation (D-0024).

## Motivation

P4-P6 on `orcarouter/Qwen3.8-27B-Uncensored` showed that the planner's
span selection - not the allocator - decided quality outcomes. Both
release fixes (P5: K-free 12.5-13.5G; P6: IQ2 span fix + Q3_K-free
9.5-10G) were changes to which native presets bracket a target and which
bulk types the fill path uses, discovered by hand from reference
measurements after release artifacts had already been built. The
allocator never made or broke a tier.

Evidence base (M9 macro KL on this model):

- Per-byte preset deltas locate toxic and golden bulk types:
  IQ2_XXS->IQ2_XS +0.1037 KLD/GiB (iq2_xs toxic; IQ2_XS preset an
  outlier like Q3_K_S +0.063/G vs IQ3_XS), IQ2_S->IQ2_M -0.1831/G
  (golden). q3_k bulk is systematically per-byte worse than IQ
  equivalents (Q3_K_S 0.2148 @ 11.245G vs IQ3_XS 0.1512 @ 11.145G).
- The fill trajectory within one span can be non-monotone: the
  IQ2_XXS->IQ2_M span peaks in measured quality near 44% fill (0.4527)
  and falls back to the endpoint preset at 100% (0.4609).
- After the two span fixes the 14-tier release curve is strictly
  monotone and every 8-10G tier beats its surrounding native presets
  (final numbers in P4 README Amendment 5).

## Proposed scope

1. `fit probe` (new subcommand): run the existing KL evaluation
   infrastructure over the full preset ladder for a given source model
   (23 presets x 5 domains, ~2 h per model, one-time). Output
   `frontier.json`: per-preset macro KL / Same-top plus a Pareto
   on-frontier classification (a preset is off-frontier if some cheaper
   preset measures better). Mechanizes the reference-point analysis that
   P5/P6 did by hand.
2. `fit plan --auto-span`: derive the span pair from `frontier.json`
   instead of a hand-written tiers.csv: skip off-frontier presets as
   endpoints, prefer bulk/fill types whose preset-lineage deltas are
   per-byte on-frontier. Must reproduce the P5 and P6 span choices on
   this model from the recorded frontier data as an acceptance test.
3. Release-mode domination self-check: after quantize + eval, run the
   G6-style check (artifact dominated by a cheaper native preset ->
   re-span to the next-best candidate and retry once). Turns the
   "size up, quality down" defect class into a pipeline guard.

## Explicitly out of scope

- No hard-coded type blacklists: "q3_k bad" / "iq2_xs bad" are
  model-specific measurements, not rules; on another model they may
  invert. Everything stays measurement-driven via frontier.json.
- No tensor-level allocation work: D-0022/D-0023 concluded allocator
  heuristics do not transfer across models, and P5/P6 confirm the wins
  were span-level. The v0.1b balanced allocator stays as-is.

## Validation plan and discipline

- New preregistration before any code affects release outputs.
- Acceptance on the development model: auto-span must reproduce the
  P5/P6 final tier table from `frontier.json` alone.
- Transfer validation on a fresh, sealed third model (never used during
  development): with zero manual span input, the produced tier ladder
  must dominate that model's own native-preset frontier per the same
  gates (zero-byte, monotone curve, no dominated tiers). Huihui and
  orcarouter are development data from now on.
- Estimated cost: ~1 day implementation, ~1 day compute for the
  third-model validation (download/convert, probe, small tier batch).
